Overall: the area is correct and consistently documented, but it is the most "image-shaped" part of the program. The three big structural issues are:

1. **Two copies of the menu/draw-list tables** (`rc2k_core/menu/tables_data.rs` 18k lines typed, `src/menu/{menus,draw_lists,lists,texts,captions,...}_store.rs` ~10k lines of `Dword` cells in IDA layout), and the stored function fields are RAL code addresses looked up at runtime by `from_ral` (Batch A).
2. **Screens are a 40-field `Screen` descriptor of step lists interpreted by one loop that talks to the outside through a dozen anonymous global flags** (Batch C, with the "screens as states" assessment below).

## "Screens as states": assessment and path

What exists. `screen_loop()` (screen_loop.rs:560) is already a small state machine: `Next::{SetUp, FrameTop, Frame, ActionCheck, Leave}` driven by `Loop::{set_up, after_first_frame, frame, keys, action, leave}`. Each of the 84 screens is a `pub const SCREEN: Screen` in its own `*_loop.rs` file (86 `_loop.rs` files), with `Step` lists at ~15 fixed hook places and, when a step is more than a call or store, a private `fn(&Entry) -> Result<(), Refused>`. Nested screens (the event flows, `confirm_leaving`) are blocking calls: `run_screen`/`screen_entry` (28 + 42 call sites) from `rc2k_core::menu::flow` driven through `Game`. The platform frame is pumped inside the loop (`crate::platform::run_frame_now`).

What is wrong with it as a design:
- **The `Screen` descriptor encodes the original's control-flow quirks as booleans.** Of ~40 fields, 25 are default on 80+ screens and non-default on 1 to 4 (`late_highlight` 1 screen, `always_asks` 1, `restart_action_check` 1, `later_frame_callback` 1, `ask_unless` 1, `no_quit_check` 2, `keys_menu` 2, `leave_at_once` 3, `action_menu` 4 (a documented original slip)). Every screen file must spell all 40 fields (`championship_new_simulation_loop.rs:56-107` is 50 lines of `None`/`false`/`&[]`), and `Loop::action` has five nested branches that depend on which booleans are set (screen_loop.rs:~750-810).
- **The loop talks to screens and flows through anonymous global cells**: `loop_flags.ended_a` (`dword_755569`), `ended_b`, `went_back` (`dword_75555D`), `back` (`dword_755561`), `event.event_done` (`dword_755980`), `captions.screen_left` (`dword_758806`), `draw_work.escaped` (`dword_755A3C`), `draw_work.action_value` (`dword_755A38`), `pages.yes_no_answer`, and `option_work.menu_sound` which doubles as "an Enter action is pending" (`0x14D`) and "no sound" (`0x6F`) (`ENTER_SOUND`/`NO_SOUND`, screen_loop.rs:93-94 and `Next::ActionCheck` at :588). That is the "reaching into global stores" the owner wants gone: a screen's result is spread over four flags that the next screen reads. The same flags appear again as the `Var` enum of `rc2k_core::menu::flow` (`Leave561`, `Ended565`, `Ended569`, `LeftA3C`, `Done`, `ModeAB40`, `Service940`... flow.rs:11-90).
- **Screens are not values.** A screen is a `const` plus functions; nothing can hold "the current screen" or return a result, so the nesting is the Rust call stack, and `Entry` (screen_loop.rs:233-262) has to carry 7 owners fetched from globals (`scene()`, `system()`, `race()`, `sound()`, `input()`, `audio()`, `menus()`) at construction.
- **Many steps are `Step::Write(|m| &m.screens.x, 0x1)`**: closures returning a field of the global store, written with a constant, to reproduce the original's `mov [dword_xxx], 1`.

Would "screens as states" be better? Yes, as a target, in a limited form. Not worth doing as a rewrite into a non-blocking `Vec<Box<dyn Screen>>` state stack first, because: the nesting is used by the event flows as a straight-line script (`rounds::race_series`, welcome, stage choice, results, review); making that non-blocking needs coroutines or an explicit script state machine, which is a large change for no player-visible gain, and the blocking pump is how the platform layer (`run_frame_now`, films) works.

Recommended path (each step independently shippable, behaviour-preserving, menus are not covered by replays so the check is the owner's run plus the existing `screen_loop` logs):
1. **C1** Give `Screen` a `Default` (all-off) and make screens write `..Screen::DEFAULT` + only what differs. Removes ~25 lines from each of the 84 files. (mechanical)
2. **C2** Group the quirk fields into small sub-structs by concern: `Asking { confirm, always_asks, ask_unless, ask_also_if, before_asking, confirmed, unasked_skips_save }`, `Keys { keys_menu, escape_leaves, short_action_check, restart_action_check, action_menu, action_saved_item }`, `Frames { frame_callback, later_frame_callback, before_first_frame, before_frame, after_blink, each_frame, no_quit_check }`. `Option<Asking>` replaces `confirm: Option<&[Step]>` + 6 related fields; the leave logic is then one `match`.
3. **C3** Replace the flag cells by one value: `enum ScreenExit { Chosen(item), Escape, LeftByFlow, ... }` carried in `Loop` / returned by `screen_loop`, with the cells kept only as long as unported readers need them (`flow.rs` `Var`). Concretely name them first (D1), then make `Loop` own `exit_reason` and have the actions return `Flow` instead of writing `back`/`ended_a`. The "went_back/back/ended_a/event_done" matrix in `Loop::action` becomes `match action_result`.
4. **C4** Make the loop itself pure: move `Loop`/`Next`/`Left` to `rc2k_core::menu::screen_machine` over a `trait ScreenHost { fn update_blink; fn run_frame(cb); fn handle_keys() -> Pressed; fn run_action(); ... }`, as already done for flows (`rc2k_core::menu::flow` + `Game`). Then the whole transition table is unit-testable without the game.
5. **C5 (later, only if wanted)** `trait ScreenState { fn enter(&mut self, ctx); fn frame(&mut self, ctx) -> Transition; fn leave(...) }` with `Transition::{Stay, SetUp, Leave(result), Push(Box<dyn ScreenState>)}`, and the event flows as an explicit script enum. Save for the "improvements" phase.

## Batch A: one source for the menu tables, function fields as enums (high value, L, medium risk)

Files: `src/menu/menus_store.rs` (2266), `draw_lists_store.rs` (1746), `lists_store.rs`, `table_routes.rs` (823), `table_calls.rs`, `run_list.rs`, `run_item_action.rs`, `navigation.rs`; `rc2k_core/src/menu/tables.rs`, `tables_data.rs` (18169, generated by the removed `tools/menu_tables`).

- **A1. Duplicate tables.** `menus_store.rs` header says "The data is the same as `rc2k_core::menu::tables`' (menus and labels), the memory the game walks by address". Same for `draw_lists_store.rs` ("the same data is `rc2k_core::menu::tables::LISTS`"). 96 menus / 567 items / 301 lists exist twice: once as `&'static MenuItem{..., on_key:[ItemFn;4], action: ItemFn}` in core, once as `[Dword; 23]` records in `src`. Proposal: `src` keeps only the four mutable item fields (string, font, behind, skip_mark) as a per-item `ItemState` array indexed by `(MenuId, item index)`, and everything else reads core's `MENUS[id].items[i]`. Drop `MenuItem::new([u32;23])`, `Menu<const N>`, `LabelList`, the 98+ literal tables and `DrawList<N>`. Effort L; risk medium (the layout is guarded by the stores' asserts; the replacement must keep the item iteration semantics `MenuItem::END`, "eight menus follow another's end mark", and the first-item-unchecked quirk in `run_item_action`/`highlighted_item`). Not mechanical for an agent beyond the generated parts; do it as one agent, menu by menu, with `cargo test -p rc2k_core` and a menu run.
- **A2. Function fields are RAL addresses looked up at runtime.** `MenuItem.on_key: [Dword;4]`, `action: Dword` hold `0x467B21`-style addresses; `table_calls::call_action/call_key/call_listed` call `ItemFn::from_ral(u32)` / `ScreenFn::from_ral` per click and per frame (`table_calls.rs:~25-100`), then a "not in a table" path to `standalone::answers(ral)` / `not_ported(...)`. Draw lists (`run_list`) walk `Dword`s ending in -1 and look each up every frame. Proposal: after A1 the tables are core's typed `ItemFn`/`ScreenFn`; delete `from_ral`, `call_listed`'s u32 interface and the "none of the items' functions" refusals (they cannot happen), `standalone::answers`/`not_ported` use here, `Named`, `ItemCall::regs()`/`Context` (register-shaped refusal report, table_calls.rs:55-70). Effort M after A1; risk low; mechanical.
- **A3. `table_routes.rs` is two 400-line `match`es** of one-line forwards (`ItemFn::ChooseKey0..7` eight arms, `Toggle*` eleven arms of `x::x().map(|_| ())`, `*VolumeUp/Down` ten arms each wrapping `Ok(())`). Proposal: make those item functions parameterised data, not 100 files: `ItemFn::Toggle(Setting)` (core already has `Setting::{MapArea,..}` in `rc2k_core::menu::player`), `ItemFn::ChooseKey(u8)`, `ItemFn::Volume { which: Volume, up: bool }`, `ItemFn::Step { setting: Setting, up: bool }`; then delete the ~60 wrapper files in `src/menu` (`toggle_*.rs` 9 files of 22 lines, `*_volume_up/down.rs` 16 files of 18 lines, `choose_key` arms, `start_a8_{one..split}`, `start_championship_*`, `time_trial_*`, `single_rally_*` (5 variants x 4 families = 20 files of 21-26 lines that differ in one number, diffed: only the header text and the player count change). The generated enum is what drives this: ItemFn would shrink from ~231 variants. Effort L, risk low, partly mechanical (a script can find the variants that differ only in an index).
- **A4. Address-based names inside the table enums.** `MenuFont::At51E824...` (tables_data.rs:1715+), `ItemFn::Toggle5180f4/Toggle7556f8/Toggle7556fc/Previous75880e/Next758812` and the modules `option_items::{toggle_5180f4,toggle_7556f8,toggle_75564c,..., next_75880e, next_758812}`. Name them by the setting they change (read `option_items.rs` and the options screens' captions; e.g. 758812 and 75880e are the two colour/quality steppers, 7556xx the toggles on the visual page). Needs the owner's confirmation per the CLAUDE.md IDA rule only for IDA names; Rust-side renames are free. Effort S-M, mechanical once names are chosen (agent can derive them from the string id of the item's label).
